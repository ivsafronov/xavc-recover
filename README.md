# xavc-recover

**Русский** · [English](README.en.md)

Восстановление видео с **отформатированной карты Sony XAVC** по посекторному образу карты.

Обычные средства восстановления (PhotoRec, testdisk, обход FAT-цепочек) с XAVC-карты не
достают **ничего** — из-за того, как камера раскладывает файлы, см.
[Почему обычные утилиты не работают](#почему-обычные-утилиты-не-работают). Этот инструмент
находит клипы прямо в образе, собирает их и проверяет, что каждый записанный файл действительно
декодируется.

> **Инструмент только читает файл образа.** Он никогда не обращается к карте. Образ снимается
> отдельно, до запуска.

## Что нужно

- Python 3.8+, только стандартная библиотека.
- Для снятия образа: `dd` (Linux/macOS/WSL) или аналог под Windows — см. ниже.
- По желанию, для проверки: `ffmpeg` / `ffprobe`.

## Шаг 0 — освободите место

**Нужно минимум 2× объёма карты.** Карта на 128 ГБ даёт образ ~128 ГБ, а восстановленные клипы
занимают ещё примерно столько, сколько реально было отснято:

```
образ (размер карты)  +  восстановленные клипы (~= отснятый материал)
```

То есть для карты, заполненной на 3/4, понадобится ~1.75× её объёма свободного места.
Освободите место заранее — если оно кончится на середине, попытка пропадёт.

Если места в обрез: вынимайте клипы по одному и удаляйте образ только после проверки
результата. **Никогда** не пишите образ на раздел самой карты.

## Шаг 1 — перестаньте пользоваться картой

Выньте её. Каждое монтирование даёт камере или ОС переписать каталог и занять освобождённые
кластеры — именно это и убивает материал. Не «исправляйте», не переставляйте карту «просто
проверить», не давайте ничему смонтировать её на запись. Если есть аппаратный блокировщик
записи — используйте его.

## Шаг 2 — снимите образ

**Linux / macOS**

```bash
# найти устройство
lsblk            # или: diskutil list

# всё устройство, не раздел — нужен exFAT-том и всё, что перед ним
sudo dd if=/dev/sdX of=/path/to/card.img bs=4M status=progress conv=noerror,sync
sync
```

**Windows (WSL)**

```powershell
wsl --mount \\.\PHYSICALDRIVE1 --bare
# далее внутри WSL:
sudo dd if=/dev/sdX of=/mnt/d/card.img bs=4M status=progress
```

**Windows без WSL** — `dd` от [chrysocome](http://www.chrysocome.net/dd), запуск **от имени
администратора**:

```cmd
dd if=\\.\PhysicalDrive1 of=C:\path\to\card.img bs=4M --progress
```

Именно `PhysicalDriveN` (весь диск), **не** `\\.\D:` (том). Проверьте номер: карта съёмная, и её
размер совпадает с картой. Ошибка здесь и перепутанные `if=`/`of=` затирают карту.

Размер образа будет ровно равен размеру устройства. Сообщение
`Error reading file: 27 (device not ready)` на последнем блоке — норма: программа попыталась
прочитать блок за концом устройства.

## Шаг 3 — посмотрите, прежде чем резать

```bash
python3 xavc_recover.py info card.img
```

Показывает геометрию exFAT и размер кластера. Если кластер не 131072, передайте
`--cluster-size`.

```bash
python3 xavc_recover.py scan card.img
```

Перечисляет найденные клипы с длительностью и статусом. **Смотрите на колонку статуса.**
`ok` — эссенция начинается ровно там, где предсказывает геометрия, клип стоит извлекать.
`DAMAGED` — проверка не прошла: обычно потому, что карта уже успела занять эти кластеры; такие
клипы повреждены или утрачены.

Индексы идут в порядке образа, это **не** порядок съёмки. Сортируйте по длительности и
времени из XML.

## Шаг 4 — извлеките

```bash
python3 xavc_recover.py extract card.img -o ./recovered
```

Пишет каждый клип вместе с его XML. Клипы, не прошедшие проверку, пропускаются с указанием
причины.

## Шаг 5 — проверьте каждый файл

Никогда не отдавайте файл, который не декодировали от начала до конца.

```bash
for f in ./recovered/*.MP4; do
  echo "== $f"
  ffprobe -v error -select_streams v:0 \
    -show_entries stream=codec_name,width,height,avg_frame_rate,nb_frames -of default=nw=1 "$f"
  ffmpeg -v error -xerror -i "$f" -f null - && echo "decode OK"
done
```

Любой вывод строки `ffmpeg` — это провал. `Invalid NAL unit size` или
`missing picture in access unit` означают, что сшивка неверна либо клип частично перезаписан.

## Имена файлов

Камера перезаписывает `PRIVATE/M4ROOT/MEDIAPRO.XML` при каждом монтировании. После
форматирования там обычно остаётся только последний клип — но **удалённая копия обычно
уцелевает** в освобождённых кластерах, и это лучший источник исходных имён, длительностей и
UMID.

Инструмент сам находит эту удалённую копию и сопоставляет её с клипами по **UMID**. Длительность
для этого не годится: на реальной карте две записи одной длины — обычное дело. Если клип нельзя
назвать достоверно, он записывается как `clip_<смещение>.MP4`, а не получает чужое имя.

Имя — не косметика: два соседних клипа, различающихся одной цифрой, это разница между «отдали
нужный дубль» и «отдали не тот». Если сопоставление неоднозначно, проверяйте вручную.

## Что восстанавливается

- **Видео MP4**: H.264, записанное разрешение и частота кадров.
- **Звук**: LPCM (`pcm_s16be`, `twos`) — без изменений.
- **Метаданные камеры**: третья дорожка `rtmd` сохраняется, то есть объектив, гамма, гироскоп и
  настройки остаются в файле.
- **Таймкод: только в XML.** Sony не пишет дорожку `tmcd` в XAVC MP4 — это верно и для
  нетронутых файлов камеры, а не артефакт восстановления. LTC лежит в
  `<LtcChangeTable tcFps="25">` в XML рядом с клипом. Большинство NLE (Resolve, Premiere) таймкод
  из `M01.XML` всё равно не читают; Catalyst Browse/Prepare — читает. Поэтому XML стоит отдавать
  вместе с клипами, но не обещать монтажёру таймкод, которого его программа не покажет.

## Почему обычные утилиты не работают

Три независимые причины:

1. **PhotoRec и подобные отбрасывают бренд.** Они ищут известные `ftyp`-бренды, а `XAVC` в их
   таблицах нет — валидные файлы отбрасываются как неизвестные.
2. **FAT-цепочка уничтожена.** Форматирование обнуляет таблицу размещения, а старые клипы к тому
   же фрагментированы — обходить нечего.
3. **Линейная вырезка идёт не в ту сторону.** Камера пишет эссенцию первой, а кластер заголовка
   *после* неё, поэтому «найти `ftyp` и копировать вперёд» даёт заголовок без данных за ним —
   «moov atom not found». Подробности в [docs/format.md](docs/format.md).

## Совместимость

Проверено на Sony **ILCE-7SM3 (A7S III)**, `XAVC-M4@2.00.00`, `AVC200_3840_2160_H422P@L52`,
50p и 59.94p, LPCM 2 канала.

Другие камеры Sony с XAVC S / XAVC S-I / XAVC HS, *вероятно*, используют ту же раскладку, но это
не проверено. Прежде чем доверять, проверьте так:

```bash
python3 xavc_recover.py scan card.img
```

Если кандидаты находятся и у них `ok` — раскладка та же. Если кандидаты есть, но все
`DAMAGED`, раскладка другая: напишите issue, приложив вывод `info` и JSON из `scan`.

Не подходит для: камер Sony с AVCHD (`.MTS`) и карт, отформатированных в другую файловую
систему.

## Ограничения

- **Перезаписанные кластеры не вернуть.** Если камера уже заняла область, эти байты утрачены.
  Смотрите статус в `scan`.
- **Один клип на кластер заголовка.** Заголовок, чьё тело упирается в кластеры предыдущего клипа,
  помечается как повреждённый, а не сшивается молча и неправильно.
- **Фрагментированные тела вне области применения.** Сшивка предполагает, что тело лежит
  непрерывно за кластером заголовка — именно так и пишет камера. Если кластеры клипа перемешаны с
  другими файлами, инструмент его не соберёт.
- Файл не пишется, пока KLV-ключ не подтвердится по предсказанному смещению.

## Чем это отличается от существующих проектов

Известные проекты по XAVC работают **на шаг позже**:

- [`open-recovery`](https://github.com/bendrape1-byte/open-recovery) берёт файлы, которые уже
  вернула утилита восстановления (полный размер, верное имя, но не открываются), и
  восстанавливает утраченный `moov`, подставляя настройки кодека из *эталонного клипа*,
  снятого в том же режиме. Ему нужно, чтобы клип уже существовал как файл.
- [`secondtake`](https://github.com/felipelimas8/secondtake) чинит повреждённые клипы XAVC S:
  ремонт заголовка, пересборка `moov`, ресинхронизация.

Оба предполагают, что у вас уже есть битый файл на диске. На отформатированной карте его обычно
нет: клип ещё никто не вырезал, а универсальные карверы либо отбрасывают его (бренд), либо дают
заголовок без данных (направление).

Этот инструмент начинает раньше — с **образа** — и, поскольку камера оставляет `moov` целым
прямо рядом с кластером заголовка, ему не приходится ничего восстанавливать. Поэтому не нужны ни
эталонный клип, ни таблица режимов: индекс не утрачен, он просто лежит не там, где его ищут.

Если у вас уже есть битые файлы и нет образа — используйте те проекты, они для этого и сделаны.
Если есть карта (или её образ) — начинайте отсюда.

## Фотографии — отдельная задача

Инструмент восстанавливает **только видео**. Фотографии на карте Sony лежат в `DCIM/` обычными
JPEG/ARW без всей этой структуры, и PhotoRec их достаёт нормально. Если на карте были только
снимки, нужен обычный карвер — этот ничего не найдёт.

У карты, писавшей видео в `PRIVATE/M4ROOT`, каталога `DCIM/` нет вообще — для видеорежима это
нормально и не означает, что фотографии потеряны.
